# 5. I2C — Inter-Integrated Circuit

**I2C (Inter-Integrated Circuit)** lets several devices communicate through
two shared signal lines: **SDA (Serial Data)** and **SCL (Serial Clock)**.
This lecture introduces the bus used by the optional TOF experiment.
The detailed driver examples can be revisited after class.

## 1. A shared channel with rules

Think of I2C as a **shared communication channel**. The STM32 and several sensors
are connected to it. **The STM32 can send a request, and a sensor can send a
reply through the same SDA line.** They take turns; SCL supplies the clock
that coordinates each bit.

Sharing the channel does not mean every sensor can speak whenever it wants.
In this setup, the STM32 is the **controller** and organizes each exchange:

1. **Select a device:** send its address. Only the addressed sensor, the
   **target**, should respond. Sensors need distinct addresses to be selected
   independently on this bus.
2. **Choose the direction:** the read/write bit says whether the STM32 will
   send data to the sensor or receive data from it.
3. **Follow the format:** I2C defines START/STOP boundaries, address and
   read/write bits, data bytes and ACK/NACK responses. The sensor separately
   defines which command/register bytes to use and how to decode its reply.

For a distance reading, the exchange means: **select this sensor → request its
distance field → let it reply → finish**. The devices do not send these words;
they send the address and data bytes required by the protocol and sensor.

Shared devices also need compatible electrical connections; see the setup guide.

## 2. Follow a reading through the supplied driver

The prepared optional `DrawOptionalTOF()` in `tutorial_app.c` uses:

```c
TOF_Sample sample = {0};
HAL_StatusTypeDef status = TOF_Read(&sample);
if (status == HAL_OK && sample.valid) {
    tft_prints(0, 9, "TOF:%5u mm", (unsigned)sample.distance_mm);
}
```

`TOF_Read()` communicates over I2C, decodes bytes and fills the passed sample.
`status` reports the I/O outcome; `sample.valid` reports measurement usability.
`sample.distance_mm` contains distance and `sample.range_status` explains range
quality. The supplied app displays dashes/errors when the checks fail.

TOF is disabled by default until its module supply, pull-ups and SHUT are
checked. This example explains the driver; it is not another required CW.

## 3. When does the variable update?

After initialization, the prepared app calls the driver during sensor-screen
updates. **Each call to `TOF_Read(&sample)` refreshes its output fields.**
Declaring a variable or copying its value does not make it update automatically.

- To get a new measurement: call the driver again.
- To use the reading: check `status == HAL_OK && sample.valid`, then use
  `sample.distance_mm`.
- To display errors: the supplied app already shows dashes/invalid status.
- Assigning `sample.distance_mm = 300` only changes the local data in memory;
  it does not ask the sensor to measure or write a setting to it.

CubeMX creates I2C initialization, HAL handles bus transfers, and the supplied
driver handles sensor registers and byte conversion. **Your task calls the driver
and uses its results.** You do not need to write encoding/decoding for this exercise.

## 4. What does Generate Code do?

CubeMX reads the `.ioc` settings and generates **peripheral initialization**.
For I2C this includes the `hi2c2` handle, `MX_I2C2_Init()` and the associated
clock/pin setup in files such as `i2c.c` and `i2c.h`.
`hi2c2` describes the I2C peripheral; it is not a sensor reading.

| What you changed | Next action |
| --- | --- |
| Only `student_tasks.c`, thresholds or app logic | Save → build → flash; no CubeMX generation needed |
| Peripheral configuration in `.ioc` | Save IOC → Generate Code → review generated changes → build → flash |

**The supplied starter is already configured.** For these tasks, edit
`student_tasks.c` and rebuild/flash. CubeMX does not generate `DrawOptionalTOF()`,
the sensor driver, or the logic that uses `sample.distance_mm`; those are
provided or written as application code.

If practicing IOC regeneration, use a project copy and the
[generation steps](../hardware/ioc-guide.md#5-savegenerate-without-losing-the-starter).
Keep the custom drivers, build sources, app calls and wiring guards.
Put task code in `student_tasks.c`; retain `USER CODE` sections for custom edits
inside generated files. Initialization configures the bus; reading data still
requires a driver call.

<summary>Further reading: register transactions, byte decoding and direct HAL calls</summary>

### Device, register and data are separate

| Item | VL53L1X example | Meaning |
| --- | --- | --- |
| Device address | 7-bit `0x29` | Which sensor? |
| Register address | `0x0096` | Which field inside it? |
| Data length | 2 bytes | How much data? |
| Returned bytes | Example: `01 2C` | Value to decode |

A **bit** is one binary digit; a **byte** contains eight bits.
The device address selects the sensor; a **register** is a numbered field inside
that sensor, such as a configuration setting or measurement result.
This sensor uses a 16-bit register address. That address width and the returned
data length are separate choices, even though both use two bytes here.
Other devices can use different registers, widths and units.

### Why HAL uses 0x52

HAL means **Hardware Abstraction Layer**. Traditional STM32F4 HAL expects the
7-bit device address shifted left once, and supplies the read/write bit:

```text
Device address: 0x29 → shift left once → HAL argument: 0x52
On-wire WRITE address byte: 0x52; READ address byte: 0x53
```

Pass **0x52 for both reads and writes**. `TOF_ADDRESS_HAL` already contains it;
do not shift twice. Device address, register address and distance are different values.

### Follow one complete exchange

This example reads register `0x0096` from the sensor at 7-bit address
`0x29`. As explained above, the transmitted address byte is `0x52` for
WRITE and `0x53` for READ.

| Step | Sender | What is sent | What it means |
| --- | --- | --- | --- |
| 1 | STM32 | START, then `0x52` | Select sensor `0x29`; STM32 will send data |
| 2 | STM32 | Register bytes `00 96` | Select its distance-result field |
| 3 | STM32 | Repeated START, then `0x53` | Select the same sensor; now it will send data |
| 4 | Sensor | Example result bytes `01 2C` | Return the two-byte measurement |
| 5 | STM32 | STOP after receiving the result | Finish the exchange |

The same SDA line carries both the request and reply. Other sensors on this
bus do not respond to this sensor's address. The returned bytes encode a value;
they are not the text characters `300`.

- **ACK = Acknowledge**; **NACK = Not Acknowledge**.
- Each byte is eight bits, **MSB (Most Significant Bit)** first, then a ninth
  acknowledge clock.
- The controller ACKs received bytes when continuing, then NACKs the final byte.
  That final NACK is normal. An address NACK can indicate a missing/wrong-address target.
- A repeated START changes direction without ending the transaction.

HAL generates the sequence; your code supplies the device, register, buffer,
length and timeout.

<details>
<summary>Signal timing and pull-ups</summary>

Ordinary data stays stable while SCL is HIGH and changes while LOW.
START is SDA falling while SCL is HIGH; STOP is SDA rising while SCL is HIGH.

Open-drain outputs pull LOW or release the line; a pull-up brings a released
line HIGH. Compatible pull-ups/signal levels require a physical check.

</details>

### Decode the result

```text
rx[0]=0x01=1; rx[1]=0x2C=44
value = 1 × 256 + 44 = 300
```

```c
uint16_t value = ((uint16_t)rx[0] << 8) | rx[1];
```

The shift makes room for the low byte; OR joins the non-overlapping parts.
Reversing them gives `0x2C01=11265`. Bytes `00 C8` give **200**.
The register definition supplies the millimetre unit; I2C does not.

### What is automatic, and what do you write?

**For this TOF exercise, you do not write byte-packing or decoding code.**
The supplied driver already does it; study the examples to understand its work.

| Layer | Responsibility |
| --- | --- |
| CubeMX-generated setup | Configure I2C clocks, pins and peripheral settings |
| I2C peripheral + HAL | Transfer bits/bytes, address and read/write direction, START/STOP and acknowledgements; `Mem_Read/Write` also send the specified register address |
| Supplied TOF driver | Choose device registers/commands, pack/unpack multi-byte values, wait for readiness, check range status and clear the sensor event |
| Supplied optional TOF app | Call `TOF_Read(&sample)`, check status/validity and display the result |

CubeMX does not generate the sensor's register definitions or know that two
received bytes represent a distance. With a direct HAL call you receive raw
bytes and must interpret them, or use a driver that already does so.

<details>
<summary>Optional: direct HAL register read — already handled by the supplied driver</summary>

This study example assumes sensor initialization. The normal task uses
`TOF_Read()`, including its readiness, status and event handling.

```c
static HAL_StatusTypeDef ReadDistanceRegister(uint16_t *value)
{
    if (value == NULL) return HAL_ERROR;
    uint8_t rx[2] = {0};
    *value = 0;
    HAL_StatusTypeDef status = HAL_I2C_Mem_Read(
        &hi2c2, TOF_ADDRESS_HAL, 0x0096U,
        I2C_MEMADD_SIZE_16BIT, rx, sizeof rx, 25U);
    if (status == HAL_OK)
        *value = ((uint16_t)rx[0] << 8) | rx[1];
    return status;
}
```

| Argument | Meaning |
| --- | --- |
| `&hi2c2` | STM32 bus instance |
| `TOF_ADDRESS_HAL` | Shifted device address, 0x52 |
| `0x0096U` | Distance register |
| `I2C_MEMADD_SIZE_16BIT` | Two register-address bytes |
| `rx, sizeof rx` | Buffer and two returned data bytes |
| `25U` | Blocking-operation timeout in milliseconds |

`Mem_Write()` writes registers; `Master_Transmit/Receive()` transfer raw bytes
without inserting register addresses. `IsDeviceReady()` checks address acknowledgement.

</details>

**ACK** means a device responded; **HAL_OK** means the HAL operation completed.
Neither proves correct register selection, byte order or a valid physical range:

```text
Communication succeeded? → Measurement valid? → Display distance
```

</details>
